# SMB Export Audit — 2026-08-01

## Trigger

Restoring a `.smb` backup generated by our exporter (`packages/meet-app/src/main/smb.ts`) into real Splash Meet Manager 11 failed with Access's stock overflow error:

> The field is too small to accept the amount of data you attempted to add.

This happened both restoring into Splash 11.84754 and (per the exporter's own hardcoded `geologix.ini` version string) the nominal target 11.84087 — so it's not a Splash version-compatibility issue. It's a bug in what we write.

## Bug: `DSQITEM.OPTIONS` overflow (root cause, confirmed)

**Where:** `config/dsq-codes.json` → consumed by `packages/meet-app/src/main/smb.ts:73` (`{ name: 'OPTIONS', type: 'S', size: 5 }`).

**What's wrong:** every entry in `config/dsq-codes.json` has an `"options"` key holding a human-readable tag list instead of a value that fits the 5-character field:

| value | count |
|---|---|
| `"INDIVIDUAL,RELAY"` (17 chars) | 43 |
| `"INDIVIDUAL"` (10 chars) | 3 |
| `"RELAY"` (5 chars — fits, coincidentally) | 24 |

46 of 70 entries overflow. This gets written straight through into the gbin `OPTIONS` field on export, and Access rejects it on restore.

**What real Splash actually stores there:** queried `DSQITEM.OPTIONS` directly (via `Microsoft.ACE.OLEDB.12.0`) from real, populated Splash meet databases (`Championnats canadiens 2026 V9.mdb`, `CQS Piscine 2026 - CSSG.mdb`, both under `C:\ProgramData\Meet Manager\Meets\`). Real values are 5-digit numeric codes, not text:

```
80600, 80400, 80200, 00000
```

Exact bit/digit meaning not yet reverse-engineered — need more real samples across different `CODE`/`NAME` combinations to map digit positions to semantics (current working guess: leading `8` may be a fixed prefix, middle digits look like an "applies to" subcode, e.g. `600` vs `400` vs `200`). `00000` shows up on unnamed rows so is likely the "no options set" default — safe fallback.

**Fix:**
1. `config/dsq-codes.json`'s `"options"` field is doing the wrong job — it currently drives what we write into a field that Splash treats as an opaque numeric code, not a human-readable applies-to tag. Either:
   - stop trying to populate real `OPTIONS` content until the encoding is understood, and just write `"00000"` (confirmed valid, matches real null/default rows), or
   - reverse-engineer the digit encoding from more real samples and generate the correct code.
2. Either way, add a hard truncate/validate step in `smb.ts` before writing any `S` field — clamp to `col.size` and log a warning if truncation actually drops data, so a future bad config value fails loud in dev instead of producing a silent Access overflow at restore time on someone else's machine.
3. Worth the same truncation safety net generically for every `S` field, not just `OPTIONS` — this class of bug (config/data longer than the declared gbin column width) isn't guaranteed to be unique to this one field.

## Methodology (for next audit)

Real Splash `.mdb` files are plain Jet/ACE databases — no special tooling needed, just:

```powershell
$conn = New-Object System.Data.OleDb.OleDbConnection("Provider=Microsoft.ACE.OLEDB.12.0;Data Source=<path.mdb>;")
$conn.Open()
$conn.GetSchema("Columns") | Where-Object { $_.TABLE_NAME -eq "DSQITEM" } | Select-Object COLUMN_NAME, DATA_TYPE, CHARACTER_MAXIMUM_LENGTH, NUMERIC_PRECISION
```

`DATA_TYPE` 2 = `SmallInt` (Splash `I;16`), 3 = `Integer`/Long (Splash `I;32`), 130 = `VarWChar` (Splash `S;N`, `CHARACTER_MAXIMUM_LENGTH` = N; blank length = memo/`M;0`), 7 = `Date` (Splash `D;32`).

Real populated meet files live in `C:\ProgramData\Meet Manager\Meets\*.mdb` on any machine with Splash installed — good source of ground truth for both schema *and* real data values (like the `OPTIONS` codes above), much more reliable than reverse-engineering from `.smb` exports alone since exports are a lossy/curated subset of the real schema (confirmed: even 11.84754's exporter drops tables like `OFFICIAL`, `JUDGE`, `COACH`, `BIOGRAPHY`, `TIMINGDATA`, `BSPICTURE` that exist in the real db).

## Bug: Splash crashes viewing any beach heat — access violation opening the Results module

After the fixes above, restoring into real Splash succeeded (DSQ codes and combined-events points confirmed visible) — but generating beach heats and opening the Results module crashed with an access violation immediately, before entering any results:

```
Zugriffsverletzung bei Adresse 02DC78D3 in Modul 'Meet.exe' (Offset 25F78D3). Lesen von Adresse 0000000C.
```
(Access violation reading address `0x0000000C` — a nil-object field dereference, offset 12 bytes into the object.)

Call stack bottoms out in `resultDM.TModulResultFactory.HandleNotification` (top frame — the actual fault), reached via `heatBOImp.THeat.VerifyStatus`/`UpdateStatus` → a notification dispatch → `modulMain`/`BSMessages` → back into `modulResult`. Reproduced identically on a heat with **zero** results entered, and on the very first heat auto-focused when the Results module activates (`FocusLastEventHeatNode`) — so it's unconditional on heat/results content, not a data-value bug.

**First hypothesis, ruled out:** `generateHeatsBeach` (`db.ts`) intentionally pools entries across every age group in a beach event (no per-agegroup split, unlike pool), leaving `heat.agegroupid` `NULL` — plausible nil-AgeGroup dereference in `THeat.VerifyStatus`. Shipped a `saveSMB`-time backfill (`HEAT.AGEGROUPID` ← `MIN(agegroupid)` from the heat's own members) and had the user re-test with a genuinely restarted meet-app (Electron's main process doesn't hot-reload). **Crash was bit-for-bit identical after the fix** (same address, same offset, same "reading 0x0000000C") — confirmed via direct `Microsoft.ACE.OLEDB.12.0` query against the actual crashed `.mdb` (`test.mdb`, 2026-08-01) that every restored `HEAT.AGEGROUPID` was already non-null (the backfill worked) — so this wasn't the (or the only) cause. Kept the backfill (it's a real, confirmed-correct fix for a real gap — a heat with a null age-group FK is never going to be *more* correct in Splash's world) but kept looking.

**Second hypothesis, also ruled out:** `RECORDLIST`/`RECORDAGEGROUP`/`RECORDLISTAGEGROUP`/`RECORD`/`RECORDSPLIT`/`RECORDPOSITION` — Splash's record-checking tables — were listed in `smb.ts`'s `allTableNames` but had no `SMB_TABLES` `ColDef` block, so no gbin file was written for them at all, unlike a real Splash database which always has them present (0 rows if unconfigured). Added them as `stub: true` (always-present, 0-row) tables. **Also bit-for-bit identical crash after a genuine restart + fresh export.** Kept the fix (it's real — a live Splash-native restore of the *same* LXF entries, decoded separately below, does carry a `RECORDAGEGROUP` row where ours had none) but it wasn't the cause either.

**Actual root cause, confirmed by direct comparison against a real Splash-native export of the identical data:** the user built a fully independent control file — `splashmeet.smb` — by importing the *same* entries LXF straight into real Splash and letting Splash generate its own heats natively (no meet-app export code involved at all). **That file opens heats with no crash.** Decoding both `SWIMSTYLE` tables (via `decodeGbin`, `tsx` one-off scripts) for the same custom style ("Drapeau Sur Plage", LENEX swimstyleid 601) side by side:

| Field | Our import (`lenex.ts`, crashes) | Real Splash's own import (works) |
|---|---|---|
| `STROKE` | `1` (claims Freestyle) | `0` |
| `TECHNIQUE` | `null` | `0` |
| `CODE` | `null` | `"ID601"` |

Neither `config/template_pool.lxf` nor `config/template_beach.lxf` ever sets a `<SWIMSTYLE stroke="...">` attribute — every style we import is a custom lifesaving discipline, not a FINA-catalog stroke. `encodeStroke()` (`lenex.ts`) silently defaulted an unrecognized/absent `stroke` attribute to `1` (Freestyle) instead of `0`. Real Splash's own LXF importer represents a non-catalog style as `stroke=0`, `technique=0`, `code="ID{swimstyleid}"` — its genuine "I don't recognize this style" convention (already known for the `code="ID0"` pause/break placeholder case, just not generalized). `(stroke=1, technique=null)` is a combination real Splash data never contains. `TModulResultFactory` — a factory, by name, for picking a per-style result-handling strategy — is the prime suspect for dereferencing something nil when handed that invalid combination.

**Fix (applied, also ruled out — third wrong turn):** `encodeStroke()`'s default changed from `1`→`0`; `importLenex`'s `upsertStyle` now also writes `technique=0` and `code='ID{swimstyleid}'` whenever `stroke` resolves to `0`. Kept — it's a real, confirmed-correct match to Splash's genuine encoding — but the user retested with **both** a genuine app restart **and** a fresh meet creation (re-triggering the template import, required since this bug only affects newly-imported `swimstyle` rows) and got the **exact same bit-for-bit-identical crash** again. Three independent hypotheses now ruled out this way in a row, each confirmed via hard evidence, not assumption.

**Actual root cause, found by systematically diffing every table** (not guessing field-by-field) between our fresh `.smb` (post all three fixes, still crashing) and `splashmeet.smb` (real Splash, works), tracing one full event→agegroup→heat→result chain via `decodeGbin` + `tsx` one-off scripts: **`HEAT.RACESTATUS`**. Real Splash's own heats for this event use `RACESTATUS=2`. Ours used `RACESTATUS=4` — never 2. Confirmed this isn't a one-off by sampling `HEAT.RACESTATUS` directly (via `Microsoft.ACE.OLEDB.12.0`) across three *separate*, real, populated Splash competition databases already on this machine (`CQS Piscine 2026 - CSSG.mdb`, `CSRN 15 février 2026.mdb`, `SplashRouville 12 juillet 2026.mdb`): all three use exclusively `{2, 5}` for `RACESTATUS`. Never `4`. Our own restored `test.mdb` (from the very first crash report) was the only file sampled with `RACESTATUS=4` anywhere.

`racestatus` is our own invented internal encoding (`decodeHeatStatus()`/`validateHeat()`/`invalidateHeat()` in `db.ts`): we only ever write `4` (generated/seeded, not yet officially validated) or `5` (validated/locked). `5` happens to coincide with Splash's own "validated" value, which is exactly why validated heats never crashed and this took so long to isolate — but our `4` collides with a value real Splash's own heat generator simply never produces for that state, and lands directly in the one field the crashing functions exist to interpret: `heatBOImp.THeat.VerifyStatus`/`UpdateStatus`. Unlike the three ruled-out hypotheses, this explains every observation at once: crashes on every heat unconditionally (every heat we ever generate gets `racestatus=4`), crashes with zero results entered (state mismatch, not a data-content issue), and was invisible to the two agegroup/record-table fixes and the swimstyle fix because none of them touched this field.

**Fix:** `saveSMB` now remaps `racestatus` `4`→`2` on export (same pattern as the existing `swimevent.round` remap, right above it in the file) and `restoreSMB` remaps `2`→`4` back on import, so meet-app's own heat-status logic keeps working correctly on a Splash-native `.smb` restored into meet-app too — the same symmetry the round remap already has. This is an **export/import (`smb.ts`) fix, not an LXF-import (`lenex.ts`) one** — unlike the swimstyle fix, this does *not* require re-importing the LXF meet structure. A plain re-export of the existing meet (after restarting meet-app to pick up the code change) should be enough to test it. Regression test: `tests/smb.test.ts` "remaps racestatus 4 ... to Splash's own 2 on export, and back on restore". **Not yet re-confirmed against real Splash** — next step is restart → re-export (no fresh meet needed this time) → restore → open-heat.

The `HEAT.AGEGROUPID` backfill, `RECORD*` stub-table, and `SWIMSTYLE` stroke/technique/code fixes above are all kept (each is a real, confirmed-correct gap relative to genuine Splash data) but **none of them were the cause** of this particular crash — worth remembering if a *different* Results-module crash shows up later, since those fixes address real but separate issues, and this session leaned hard on "get a genuine Splash-native control file and diff every table with `decodeGbin`" rather than guessing from the stack trace alone — that discipline is what actually found each real fix (the LXF-style bug via style diff, this one via a full event-chain diff and cross-checking real competition data), while guessing from the crash trace alone produced three plausible-sounding but wrong theories in a row.

## Bug (unrelated to the .smb round-trip, found via a parallel diagnostic): beach numbers crash importing entries against Postgres

While setting up a shared-Postgres control test to isolate whether the Results-module crash above lives in `.smb` gbin encoding specifically (vs. meet-app's underlying data) — connect Splash and meet-app to the same live Postgres database, no `.smb` file involved at all — importing a beach meet's entries LXF into the Postgres-backed meet-app failed outright with:

```
Erreur: PG: for SELECT DISTINCT, ORDER BY expressions must appear in select list
```

This blocked the control test entirely (fails before any heat/Results-module code runs), but is a real, independent bug: `generateBeachNumbers()` (`beachNumber.ts`), called automatically during entries import for beach meets, had two SQLite-only query patterns that silently passed on SQLite but are invalid on Postgres:
1. `SELECT DISTINCT c.clubid, c.code, c.name ... ORDER BY UPPER(c.code)` — `UPPER(c.code)` isn't in the `SELECT DISTINCT` list. SQLite tolerates an `ORDER BY` expression that isn't a select-list item; Postgres requires exact match (matches the error text exactly).
2. `... ORDER BY ag.agemin, ag.agemax, ag.gender, a.lastname COLLATE NOCASE, a.firstname COLLATE NOCASE` — `COLLATE NOCASE` is SQLite-specific syntax, invalid on Postgres. A third instance of the same `COLLATE NOCASE` (no `DISTINCT` involved there) was also found in `db.ts:3425` (entries-by-event report sort) via a full-codebase audit for both patterns.

**Fix:** query 1 now selects `UPPER(c.code) AS code_upper` and orders by that alias. Query 2 drops `DISTINCT` (unneeded — the caller already dedupes by `athleteid` in JS afterward, so it doesn't change results) and drops `COLLATE NOCASE` (also doesn't affect final output — display order is re-sorted with proper locale comparison downstream; this only affected which duplicate row won an internal dedup tie). `db.ts:3425` switched to `LOWER(a.lastname), LOWER(a.firstname)` (portable, and this one *is* user-facing report order, unlike beachNumber.ts's internal ordering).

**This is a real coverage gap, not just a one-off bug**: `beachNumber.ts` had zero PG-backend test coverage before this — none of `heat-generation.test.ts`/`schema.test.ts`/`combined-events.test.ts`'s `describe.each(['sqlite','pg'])` parity suite touches it. Added a new `describe.each` block to `tests/beach-number.test.ts` covering exactly this ("Beach number generation backend parity") and **ran it against a real, live Postgres instance** (the project's documented portable Postgres, `%UserProfile%\pgsql-portable`, started for this) rather than trusting SQLite-only green — 39/39 pass there now, confirming the fix actually resolves the reported error and not just that it compiles.

**Second and third rounds of the same class of bug**, hit immediately after fixing the above and continuing the same import: `INSERT OR IGNORE`/`INSERT OR REPLACE` (SQLite-only syntax, no Postgres equivalent) in three more places — `lenex.ts`'s `relayposition` insert during relay-entry import, `index.ts`'s `seedDsqCodes` (`dsqitem` seeding, runs on every new meet), and `livePush.ts`/`lenex.ts`'s `bsglobal` upserts for live-push config. Fixed each:
- `relayposition`: switched to a plain `INSERT` — `OR IGNORE` was already a no-op even on SQLite (no unique constraint exists on `(relayid, relaynumber)` in `schema.ts`, and `relayid` is always freshly minted via `nextId()` just above, so there's never an actual conflict within one import), so this changes nothing in practice while fixing the syntax.
- `dsqitem`/`bsglobal`: switched to the standard `INSERT ... ON CONFLICT (...) DO UPDATE SET ...` form, which SQLite (3.24+, bundled by `better-sqlite3`) and Postgres both support natively — no backend branching needed, unlike `smb.ts`'s existing `isPg` duck-typing branch (kept as-is there since it's already correct).

**`lenex.ts` (the LXF importer) has the same zero-PG-coverage gap** `beachNumber.ts` had — not fixed with a new test this pass (both bugs found were basic SQL-syntax-validity issues, not subtle logic bugs, so fixed with high confidence from the pattern above rather than new test scaffolding), but worth closing properly later the same way `beach-number.test.ts` was.

**Fourth round, a different sub-species of the same class**: not a syntax error this time — `[DSQ] Error seeding codes: Error: PG: value too long for type character varying(5)` from `seedDsqCodes` (`index.ts`). Root cause is the *exact same* `dsqitem.options` field already covered in the `OPTIONS;S;5` bug section near the top of this doc, but hitting a different code path: `connectionManager.ts` deliberately declares `dsqitem.options` as `VARCHAR(5)` on Postgres specifically to match real Splash's own column width (this table can be shared live with an actual Splash instance connected to the same database) — but `seedDsqCodes` was still writing the long human-readable tag ("INDIVIDUAL,RELAY", up to 17 chars) straight into it. SQLite has no column-width enforcement at all, which is why this never surfaced there. Unlike the `.smb`-export fix (which could safely blank `OPTIONS` to `"00000"` since nothing reads it back from an exported file), **this column is actually read at runtime** — `HeatsPage.tsx`'s DSQ-code dropdown filters codes by individual-vs-relay applicability via `d.options.includes(eventType)` — so blanking it would have silently broken that filter. Fixed by compacting to single-letter codes (`compactDsqOptions()` in `index.ts`: `"IR"`/`"I"`/`"R"`, all well under 5 chars) that still carry the same meaning, and updating `HeatsPage.tsx`'s filter to match both the new compact form and the old long form (for meets already seeded before this fix — `seedDsqCodes` only runs at meet creation, not on every launch, so existing meets keep whatever was written previously).

## Finding: live-Postgres sharing order matters, confirmed both directions

Two more rounds on the shared-Postgres control test, isolating write order specifically:

- **meet-app connects first** (writes its own schema/data), Splash connects second → Splash refuses to open the meet at all: `Error when trying to open meet. DB [meetmgr]. File/Database contains wrong data.` This is a different failure than the Results-module access violation — a generic up-front sanity check, not a crash once inside. Consistent with everything already known in this doc: meet-app's `schema.ts` is a real subset of Splash's actual schema (missing columns like `AGEGROUP.AFINAL8LANES`, the `RECORD*` tables, etc.) — creating tables from that subset first and then having Splash try to recognize them doesn't work. This matches the pre-existing documented guidance (`packages/meet-app/CLAUDE.md`, PG testing section) to always let Splash initialize the schema first when sharing a live database — not a new bug, a re-confirmation of an existing constraint.
- **Splash connects first** (fresh/untouched database, auto-creates its own real schema), meet-app connects second and does the import/heat-generation/results, Splash reopens third → **works**, no crash, no "wrong data" error. This is the clean, decisive result the whole control test was built to get: it confirms the earlier Results-module access violation is specifically caused by something in meet-app's `.smb` export (`smb.ts`) — not by meet-app's underlying data model or its Postgres writes in general, since the exact same data written live to Postgres reopens fine in Splash.

**One real gap found in the working (Splash-first) path**: meet-app's own UI showed the beach meet as a **pool** meet. `importLenex`'s `MEET_TYPE` auto-detect (any `swimstyleid >= 600` → `BEACH`) only runs inside meet-app's own LXF import — since Splash did the import this time, that code never ran, so `bsglobal.MEET_TYPE` stayed unset and the app fell back to its `POOL` default. **Fixed**: `connectToPg` (`connectionManager.ts`) now runs the same auto-detect on connect, whenever `MEET_TYPE` isn't already set — so connecting to a database someone/something else populated (not just Splash — any external writer) infers the right meet type instead of silently assuming pool.

## Bug: existing meet-app databases missing `agegroup.afinal8lanes` — `no such column` exporting `.smb`

Adding `AFINAL8LANES` to `smb.ts`'s `AGEGROUP` export list (see the finding above) surfaced a separate, pre-existing gap: `afinal8lanes` was added to `schema.ts`'s `CREATE TABLE IF NOT EXISTS agegroup` a session before this one (per `packages/meet-app/CLAUDE.md`'s notes on the `splash-schema-contract` test that caught it) — but `CREATE TABLE IF NOT EXISTS` is a no-op once a table already exists, so it never reached any database created before that column was added. `smb.ts` then tried to `SELECT afinal8lanes FROM agegroup` against exactly such a database and got `no such column: afinal8lanes`. Same underlying class of problem as `dsqitem.name_en` (which *did* get a targeted Postgres-only backfill in `connectionManager.ts`, but nothing for SQLite, and nothing generic).

**Fix:** added `runColumnBackfills()` (`schema.ts`) — a small, explicit list of `{table, ddl}` column backfills, each run via `ALTER TABLE ... ADD COLUMN ...` wrapped in try/catch (ignoring "already exists" failures; `ADD COLUMN IF NOT EXISTS` isn't portable across SQLite versions). Wired into `runSchemaInit()` (covers every SQLite connection) and separately into `connectToPg()` (which never called `runSchemaInit()` at all). `afinal8lanes` is the first entry; the same list is the right place for any future schema-drift column found this way, instead of a one-off fix per column. Regression test: `tests/schema.test.ts` "backfills agegroup.afinal8lanes onto a database that predates the column" (simulates the pre-column table directly, runs on both backends).

## Status at end of day, 2026-08-01 — Results-module crash unresolved, deprioritized

**The Results-module access violation (`TModulResultFactory.HandleNotification`, opening any heat in a restored beach `.smb`) is still not fixed.** After the fifth batch of fixes below (`AGEGROUP.AFINAL8LANES`, `RECORDAGEGROUP` sentinel row, beach `MEETVALUES.COURSE`, plus the `agegroup.afinal8lanes` schema-backfill fix that was blocking the export entirely) was live-tested — same bit-for-bit-identical crash, same address, same offset, same "reading 0x0000000C" — as every batch before it. **Five** rounds of fixed-and-kept-but-ruled-out hypotheses now: `HEAT.AGEGROUPID` nulls, missing `RECORD*` tables, `SWIMSTYLE` stroke/technique/code encoding, `HEAT.RACESTATUS` 4-vs-2, and this fifth batch. All five fixes are real, confirmed-correct gaps relative to genuine Splash data and are kept — none of them were wrong to fix — but none of them is *this* crash's cause.

**Explicitly deprioritized by the user as of this point — not a priority use case.** Picking this back up later should start from the shared-Postgres control test result (see the "live-Postgres sharing order matters" finding above): that test proved conclusively the crash is specific to something in `.smb`'s gbin encoding (`smb.ts`), not meet-app's underlying data model, so the search space is narrower than it looks from the list below. The next productive move, if resumed, is probably back to the full-table `decodeGbin` diff-against-`splashmeet.smb` technique that found the `RACESTATUS` and `SWIMSTYLE` bugs — diffing tables not yet individually compared (`SWIMRESULT`'s full field set, `CLUB`, `ATHLETE`) rather than another single-field guess.

**What this investigation produced beyond the (still open) crash itself — all real, all kept, all worth having independent of whether the crash ever gets fixed:** the `.smb` restore-into-Splash compatibility fixes (`DSQITEM.OPTIONS` overflow, `RELAY` field widths, `RELAYSPLIT`, and the five batches above), a string of genuine SQLite-vs-Postgres portability bugs across `beachNumber.ts`/`lenex.ts`/`index.ts`/`livePush.ts`/`db.ts` (see [[meetapp-sqlite-pg-sql-portability]] memory), a `MEET_TYPE` auto-detect gap on Postgres connect, and a generic schema-column-backfill mechanism (`runColumnBackfills`) that closes a whole class of "new column never reaches existing databases" bug, not just the one instance that surfaced it.
